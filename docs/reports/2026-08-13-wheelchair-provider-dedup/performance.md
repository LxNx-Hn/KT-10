# 휠체어 경로 공급자 호출·응답시간 검증

측정일: 2026-08-13 (Asia/Seoul)

## 변경 전 실측 기준선

동일 로컬 Docker 구성에서 기존 전체 추천 경로를 측정했다.

| 조건 | 표본 | p50 | p95 | 공급자 호출 |
|---|---:|---:|---:|---|
| cold | 20 | 4.6434초 | 5.3526초 | ODsay search 20, loadLane 20, ORS 성공 캐시 생성 60, TMAP 성공 캐시 생성 60 |
| warm | 20 | 3.6824초 | 5.6302초 | 경로 공급자 0, NIM 20 |

이 기준선은 후보마다 보행 공급자를 반복하고 초기 응답에서 loadLane·NIM까지
기다리던 구조다.

## 변경 후 실측

### canonical AI 경로 생성 cold

서로 다른 미측정 OD 20개, `candidate_limit=5`, `uses_wheelchair=true`,
`avoid_stairs=true`로 `/labeling/candidates`를 순차 호출했다. route-feature 캐시는
해당 OD에 없었고, 오류 표본을 성공 지연시간에 섞지 않았다.

| 표본 | 성공 | p50 | p95 | 최소 | 최대 |
|---:|---:|---:|---:|---:|---:|
| 20 | 20 | 1.4895초 | 1.6388초 | 1.1607초 | 1.8965초 |

별도 10개 cold OD 묶음의 공급자 증분은 ODsay network 10,
ORS 성공 캐시 생성 10, TMAP 성공 캐시 생성 0이었다. 즉 이 표본에서는 요청당
ODsay 1회와 직접 ORS wheelchair 1회만 필요했고, 저상버스 또는 공식 접근 가능
출구가 확인되지 않아 후단에서 탈락할 대중교통 후보에는 ORS를 호출하지 않았다.

### warm 및 동시 요청

구서역→남포역 동일 좌표·옵션을 canonical AI 경로 생성 API로 20회 호출한 결과:

| 표본 | HTTP | p50 | p95 | 최소 | 최대 |
|---:|---:|---:|---:|---:|---:|
| 20 | 모두 200 | 0.0225초 | 0.0242초 | 0.0218초 | 0.0272초 |

동시 동일 요청 10개는 총 0.3193초에 모두 200이었다. 실행 전후 ODsay 일일
network counter, ORS/TMAP 캐시 파일 수와 최종 수정시각이 모두 같았다. 따라서
warm 외부 경로 API 호출은 0회다.

동일한 로컬 Backend 공개 API `/api/routes/recommend`의 warm 20회는 모두 200,
경로 1개를 반환했고 p50 0.0505초, p95 0.0853초였다.

## 호출·정확성 계약

- ODsay 후보 검색은 요청당 최대 1 network 호출이며 cache/single-flight를 쓴다.
- 좌표 7자리와 휠체어·계단 옵션이 같은 실제 보행구간은 요청 내부 Task와 ORS
  영구 cache/single-flight를 공유한다.
- 한 후보의 출발·도착 보행구간은 병렬 계산한다.
- TMAP은 사용자 휠체어 요청에서 `collect_cached()`만 사용한다.
- TMAP 성공 응답은 명시적 schema/data version이 바뀔 때까지 유지하며,
  쓰기 cache가 없어도 이미지 내 `data/precomputed/tmap`을 읽는다.
- 공식 접근 가능 지하철 출구는 로컬 정규화 CSV만 적용한다.
- 계단 회피, ORS wheelchair 제약, extra-info 전구간 coverage가 모두 확인된
  보행구간만 남긴다.
- 알 수 없는 계단 수·경사로·저상버스·출구 접근성은 0/false/true로 만들지
  않는다. 공개 응답은 `exclude_none`으로 생략한다.

## 데이터 갱신 검증

사전수집 CLI를 실제 키로 OD 1개에 실행한 결과, ORS 검증 고유 보행구간 7개 중
TMAP과 선형이 일치한 2개만 artifact 대상이 되었고 5개는 불일치로 거부되었다.
검증된 2개에서는 공식 경사로 코드가 관측되지 않았다. 이는 경사로가 없다는
판정이 아니므로 `hasSlope=false`나 0으로 저장하지 않는다. 보고서 상태는
의도대로 `partial`이었다.

## 해석 한계

ORS와 TMAP의 서로 다른 선형은 정확성 보존을 위해 결합하지 않는다. 따라서
TMAP 경사로 coverage는 데이터 갱신 OD 목록과 양 공급자의 유사 선형 범위에
한정된다. 현장 미매핑 계단·공사·적치물·고장·문/게이트 개방 상태는 ORS/OSM
계약만으로 확인할 수 없으며 API의 데이터 한계 문구를 유지한다.
